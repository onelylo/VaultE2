# Vault2E (VaultChat Enterprise) — Threat Model

**Auditor:** Senior Security Architect  
**Date:** 2026-08-17  
**Scope:** 25-threat model covering Vault2E's full stack (ECDH P-256, AES-256-GCM, PBKDF2 600K, HMAC-SHA256 JWT, PostgreSQL, Socket.io, Express.js, Dexie IndexedDB).

---

## Threat Catalog

| # | Threat | Attacker Capability | Affected Component | Current Protection | Missing Protection | Severity | Mitigation |
|---|--------|---------------------|--------------------|--------------------|-------------------|----------|------------|
| 1 | Honest-but-curious server | Server sees all encrypted traffic, metadata, sender/recipient IDs, ciphertext lengths, timestamps. Does not modify data. | server/src/index.ts, PostgreSQL messages table | All message content is AES-256-GCM encrypted client-side. Server never sees plaintext. Encrypted attachment blobs. Encrypted vault (PBKDF2+AES-GCM). | Sender/recipient IDs visible. Ciphertext length leaks plaintext size. Message frequency/volume observable. Timestamps visible. | MEDIUM | Implement Sealed Sender (encrypt sender ID). Pad messages to fixed blocks. Reduce metadata retention. Consider message expiration policies. |
| 2 | Compromised application server | Full read/write access to PostgreSQL, filesystem, Socket.io relay. Can modify API responses, inject messages, alter public keys. | server/src/index.ts, server/src/db/index.ts, PostgreSQL, uploads/ directory | Message content encrypted client-side (server cannot read). JWT signing with HMAC-SHA256 (JWT_SECRET). Rate limiting on auth endpoints. CSP + Helmet headers. | Server can substitute public keys in transit (no certificate pinning). Server can inject messages into Socket.io relay. Server can modify channel key envelopes. Server can read encrypted vault (offline brute-force possible with weak password). | HIGH | Implement certificate pinning. Add client-side key verification for all critical operations. Consider server transparency logs. Use strong passwords + Argon2id for vault wrapping. Add audit logging for all key operations. |
| 3 | Database leak | Attacker gains read access to PostgreSQL data (SQL injection, backup leak, disk access). | PostgreSQL (embedded-postgres), server/src/db/schema.sql | All message content is AES-256-GCM encrypted. Attachment blobs encrypted. Vault encrypted with PBKDF2+AES-GCM. Public keys are not secret. | Encrypted vault is offline-brute-forceable with weak password (PBKDF2 600K is strong but not impervious to nation-state). Ciphertext + IV pairs could be brute-forced if password is weak. Metadata (sender, recipient, timestamps, message count) fully exposed. | HIGH | Enforce strong password policy (min 12 chars, complexity). Consider Argon2id for vault wrapping. Encrypt database at rest (PostgreSQL TDE or disk encryption). Minimize metadata retention. Implement data retention policies. |
| 4 | Attachment storage leak | Attacker gains read access to uploads/ directory on server filesystem. | server/src/index.ts (multer storage), uploads/ directory | Attachment binaries are AES-256-GCM encrypted before upload. Metadata (filename, size, mime type) encrypted separately. | If attacker also has database access, can correlate encrypted attachments with messages. Attachment encryption key is same as conversation key -- if that key is known, all attachments in conversation are exposed. | MEDIUM | Encrypt database at rest. Use per-attachment random keys (encrypt attachment with random key, encrypt random key with conversation key). Implement attachment access logging. |
| 5 | Malicious server operator | Server operator has full control: can read all data, modify API responses, inject messages, alter keys, log all traffic, brute-force vaults offline. | Entire server stack, PostgreSQL, uploads/ | Client-side E2EE prevents server from reading message content (assuming strong password). JWT_SECRET protects auth. | Server can: (a) substitute public keys to perform MITM, (b) inject messages via Socket.io, (c) modify channel key envelopes, (d) brute-force vaults offline, (e) log all metadata, (f) refuse to deliver messages, (g) replay old messages. | HIGH | Client-side key pinning (TOFU). Certificate pinning. Consider decentralized architecture. Server-side audit logging for key operations. Strong password enforcement. Message delivery receipts with client-side verification. |
| 6 | Network attacker (MITM) | Can intercept, modify, drop, or replay TLS traffic. Can perform DNS hijacking. Cannot break TLS 1.3. | TLS transport (Socket.io WebSocket, HTTPS) | TLS 1.2+ with HTTPS. Helmet HSTS headers. CORS origin restriction (CORS_ORIGIN env var). | No certificate pinning. No client-side message authentication beyond TLS. TOFU model trusts first key seen (vulnerable to first-contact MITM). | MEDIUM | Implement certificate pinning. Add out-of-band key verification (safety numbers / QR codes). Use HPKP or mobile certificate pinning. Consider DNSSEC. |
| 7 | Stolen device | Physical access to an unlocked device. Can access Dexie IndexedDB, read memory, capture screen. | client/src/lib/db.ts (IndexedDB), browser memory | Private keys stored as JWK in Dexie (IndexedDB). Vault encrypted with PBKDF2+AES-GCM. Browser same-origin policy prevents cross-origin access. | IndexedDB is accessible if device is unlocked. Private keys in plaintext JWK in IndexedDB. No hardware-backed key storage. No biometric-gated key access. No remote wipe capability. | HIGH | Implement biometric-gated key access (WebAuthn / device keys). Add remote device revocation. Consider hardware security module (HSM) or secure enclave for key storage. Add auto-lock timeout. Implement remote wipe on device theft. |
| 8 | Compromised device | Malware with user-level access on device. Can read IndexedDB, capture keystrokes, screenshot, hook crypto APIs, read memory. | Entire client stack (browser, IndexedDB, Web Crypto API) | E2EE happens in browser context. Web Crypto API operations are in-process. | Malware can: (a) read private keys from IndexedDB, (b) intercept plaintext before encryption / after decryption, (c) capture passwords, (d) hook crypto.subtle to log keys, (e) modify encryption/decryption in transit. | CRITICAL | This is an accepted risk for all client-side E2EE. Mitigations: (a) use hardware-backed keys where possible, (b) implement tamper detection, (c) use secure enclave for key operations, (d) code integrity verification, (e) consider using a dedicated security context (e.g., iframe sandbox). |
| 9 | Account takeover | Attacker obtains user credentials (phishing, credential stuffing, password spray). | server/src/index.ts (auth endpoints), bcrypt password hashing | Bcrypt with 12 rounds for password hashing. Rate limiting: 10 requests/minute on auth endpoints. JWT with 1-hour expiry. Token blocklist on logout. Legacy SHA-256 passwords auto-migrated to bcrypt. | No multi-factor authentication. No account lockout after failed attempts (only rate limiting). No login anomaly detection. No email verification. | HIGH | Implement MFA (WebAuthn / TOTP). Add account lockout after N failed attempts. Add login anomaly detection (new IP, new device). Enforce email verification. Add suspicious login notifications. |
| 10 | Malicious Hub member | Authenticated user with MEMBER role in a Hub. Can send messages, access channel content, request channel keys. | useChannels.ts, useMessages.ts, channel_keys table | Channel AES key encrypted per-member via ECDH. Channel key rotation on member removal (best-effort). TOFU key verification for contacts. | Malicious member can: (a) read all channel messages (has channel key), (b) save/export messages, (c) spam key requests, (d) send malicious content. | MEDIUM | Implement message content moderation (client-side or trusted admin). Add channel-level access controls (read-only channels). Rate limit key requests. Consider content expiry. Implement abuse reporting. |
| 11 | Removed Hub member | Former MEMBER who was removed from a Hub or channel. May retain channel key in local cache. | useChannels.ts (key rotation), channel_keys table (envelope deletion) | Server deletes removed member's envelope from channel_keys table (index.ts:2157). Server emits channel:key_rotated event. Channel creator generates new key and redistributes. | Removed member retains locally-decrypted channel key in Dexie cache until they clear it. Key rotation is best-effort -- if creator is offline, rotation does not happen. Window between removal and rotation allows reading new messages. | MEDIUM | Force key rotation on member removal (server-mediated if creator is offline). Server should refuse to deliver messages to removed members until rotation is confirmed. Implement key revocation list. Add removal timestamp to channel metadata. |
| 12 | Malicious Hub administrator | Admin or Owner role in a Hub. Can add/remove members, manage channels, transfer ownership. | useAdmin.ts, useChannels.ts, hub_members table | RBAC enforced server-side (ADMIN, SUPERVISOR, MEMBER roles). Audit log for admin actions. | Admin can: (a) add themselves to any channel, (b) distribute channel keys to themselves, (c) read all channel messages, (d) remove other admins, (e) transfer ownership to attacker-controlled account. | MEDIUM | Implement channel-level admin separation. Require owner approval for admin actions. Add admin action audit trail with notifications. Implement separation of duties for critical operations. |
| 13 | Replay attacker | Captures a valid (ciphertext, iv) tuple and re-injects it into the system. | Network layer, Socket.io relay | AES-GCM authentication tag prevents ciphertext modification. TLS prevents network-level replay. Message IDs are unique (srv_{timestamp} or temp_*). | No application-layer replay protection. A compromised server or insider could replay old messages. No nonce/counter tracking. No message sequence numbers in encrypted payload. | MEDIUM | Add message counter or timestamp in AES-GCM AAD. Track seen nonces per peer in client-side storage. Implement server-side nonce tracking. Add message sequence numbers. |
| 14 | Message reordering | Attacker reorders messages in transit or in the database. | Socket.io relay, PostgreSQL messages table | Server stores messages with created_at timestamp and serves in order. Client uses Dexie put() with message ID (upsert). | No message sequence numbers in encrypted payload. No client-side ordering verification. If server is compromised, messages can be reordered. | LOW | Add message sequence number in AES-GCM AAD. Client should verify sequence continuity. Consider client-side ordering based on decrypted sequence numbers. |
| 15 | Message deletion | Attacker (server or insider) deletes messages from PostgreSQL or prevents delivery. | PostgreSQL messages table, Socket.io relay | Soft-delete: is_deleted flag in messages table. Client stores messages locally in Dexie (IndexedDB). Message delivery receipts (delivered, read status). | Server can hard-delete messages from database. Client has no tamper-evident proof of message existence. No message backup/integrity verification. No server commitment to message retention. | MEDIUM | Implement client-side message backup with integrity verification. Add server commitment to message retention (signed receipt). Consider message anchoring (hash chain or blockchain timestamp). Implement delivery receipts with client-side verification. |
| 16 | Message substitution | Attacker replaces a legitimate message with a different message (same ID or re-injected). | Socket.io relay, PostgreSQL messages table | AES-GCM authentication tag prevents ciphertext modification. Message IDs are unique. TOFU key verification prevents key substitution. | If server is compromised, can substitute ciphertext with attacker-encrypted version (using known key). No message integrity proof independent of encryption. | MEDIUM | Add message authentication separate from encryption (HMAC with client-side key). Implement message signatures. Add message sequence numbers for ordering verification. |
| 17 | Identity-key substitution | Attacker replaces a user's public key with their own, enabling MITM. | server/src/index.ts (public key storage), TOFU validation (crypto.ts:568-617) | TOFU model: first-seen public key pinned in trustedKeys Dexie table. Key rotation signed with ECDSA. Rotation rate-limited (3/hour). Server verifies rotation signature. | First-contact key exchange is unauthenticated (no out-of-band verification). Server can substitute public keys before first contact. No certificate authority or trust anchor. | HIGH | Implement out-of-band key verification (safety numbers / QR codes). Add certificate pinning. Consider trust-on-second-use with explicit verification. Implement key transparency logs. |
| 18 | Key compromise | Attacker obtains a user's ECDH private key (via device theft, malware, side-channel). | client/src/lib/crypto.ts (private key in Dexie), sharedKeysCache | TOFU key verification detects key changes after rotation. ECDSA-signed rotation chain. Rate-limited rotation. | Single ECDH private key compromise exposes: (a) all past messages (no forward secrecy), (b) all future messages (until manual rotation), (c) all channel keys for that user, (d) ability to impersonate the user. No per-device key isolation. | CRITICAL | Implement Double Ratchet for per-message forward secrecy. Implement per-device identity keys. Add remote device revocation. Preserve old keys for grace period. Consider hardware-backed key storage. |
| 19 | Backup compromise | Attacker obtains the encrypted vault from PostgreSQL and brute-forces the password. | PostgreSQL users.encrypted_private_key, users.key_salt, PBKDF2 wrapping | PBKDF2-SHA256 with 600,000 iterations. 16-byte random salt. AES-256-GCM wrapping. | If user has weak password, vault is brute-forceable (600K PBKDF2 iterations are strong but not impervious). No multi-factor key derivation. No key escrow beyond password. | HIGH | Enforce strong password policy (min 12 chars). Consider Argon2id for better GPU/ASIC resistance. Add multi-factor vault wrapping (password + device key). Implement account lockout after failed vault decryption attempts. Consider E2E backup as opt-in. |
| 20 | Push notification metadata leakage | Attacker intercepts push notifications and reads metadata (sender, timestamp, preview text). | Browser notification system (notify.ts), Web Notifications API | Vault2E uses Web Audio API oscillator for notification sounds (notify.ts). Does NOT use browser push notifications (no Notification API usage for messages). | No push notification system implemented. This is a non-issue for Vault2E. However, if push notifications are added in the future, metadata leakage is a risk. | INFO | If push notifications are added: use silent notifications with no metadata. Encrypt notification payload. Use anonymized push tokens. |
| 21 | Traffic analysis | Attacker observes message timing, frequency, size, and communication patterns. | Network traffic, Socket.io WebSocket connections | TLS encrypts content. WebSocket transport makes traffic analysis harder than HTTP. | Message timing visible. Message frequency visible. Ciphertext length reveals approximate plaintext size. Online/offline status visible. Communication graph visible (sender/recipient pairs). | MEDIUM | Pad messages to fixed sizes. Add random delays to message delivery. Implement traffic padding. Consider mix networks for high-security use cases. Reduce metadata retention. |
| 22 | Metadata leakage | Server or attacker observes who communicates with whom, when, how often, and how much. | PostgreSQL messages table, channel_members, friends, hub_members, Socket.io presence events | Encrypted content. Encrypted attachments. Encrypted vault. | Sender/recipient IDs in plaintext. Timestamps in plaintext. Message count per conversation. Channel membership lists. Friend lists. Hub membership. Online/offline status. Typing indicators. | MEDIUM | Implement Sealed Sender (encrypt sender identity). Reduce metadata retention. Implement message expiration. Consider metadata-hiding techniques (e.g., private information retrieval). Add metadata minimization policies. |
| 23 | Denial of service | Attacker floods server with requests, exhausts resources, or disrupts service. | server/src/index.ts, Socket.io, PostgreSQL | Rate limiting: auth (10/min), messages (10/sec/socket), uploads (10/min/user), key rotation (3/hour). Helmet security headers. Express rate limiting. | No rate limiting on: channel creation, channel join, friend requests, hub creation, message search. No DDoS protection (e.g., Cloudflare). No request size limiting beyond HTTP buffer (26 MB). No connection limiting per IP. | MEDIUM | Add rate limiting on all endpoints. Implement request size limiting. Add connection limiting per IP. Consider DDoS protection service. Implement backpressure mechanisms. Add circuit breakers for downstream services. |
| 24 | Compromised dependency | Attacker compromises an npm package used by Vault2E (server or client). | package.json (server and client dependencies) | No dependency auditing in CI/CD (not observed). No lockfile integrity checking. No Software Composition Analysis (SCA). | Server dependencies: express, socket.io, embedded-postgres, bcrypt, pino, helmet, multer. Client dependencies: react, vite, dexie, socket.io-client, lucide-react. Any compromised dependency could exfiltrate keys, plaintext, or tokens. | HIGH | Implement dependency auditing (npm audit, Snyk, Socket.dev). Use lockfiles with integrity hashes. Implement Software Composition Analysis (SCA). Pin dependency versions. Review dependencies before adding. Implement automated vulnerability scanning. |
| 25 | Supply-chain attack | Attacker compromises build pipeline, injects malicious code into build artifacts, or trojanizes development tools. | Build system (Vite, TypeScript compiler, npm), CI/CD pipeline | Vite builds client-side code. TypeScript provides type safety. No observed build artifact verification. No reproducible builds. No code signing. | Compromised build could: (a) exfiltrate private keys during build, (b) inject backdoor into crypto operations, (c) modify encryption/decryption to use weak parameters, (d) add hidden API endpoints for data exfiltration. | HIGH | Implement reproducible builds. Add build artifact signing and verification. Use deterministic builds. Implement CI/CD pipeline security (signed commits, protected branches). Add build-time code review. Consider using a build attestation system (SLSA). |

## Vault2E-Specific Attack Scenarios

### Scenario A: Single Key Compromise Cascading Failure

**Trigger:** Attacker obtains victim's ECDH P-256 private key from Dexie IndexedDB (device theft, #7).

**Impact chain:**
1. All past DM messages decryptable (no forward secrecy, #18)
2. All future DM messages decryptable until manual rotation (#18)
3. All channel keys for that user derivable (ECDH with each channel creator, #18)
4. Attacker can impersonate user (forge messages, #16)
5. All attachments in conversations decryptable (#4)
6. If password is weak, vault can be brute-forced for key recovery (#19)

**Current mitigation:** TOFU detects key change on next contact. Manual rotation available.
**Missing mitigation:** Double Ratchet (per-message forward secrecy), per-device keys, remote revocation, hardware-backed storage.

### Scenario B: Compromised Server Key Substitution

**Trigger:** Malicious server operator (#5) substitutes public keys in the users table before delivery.

**Impact chain:**
1. Server replaces Alice's public key with attacker's key
2. Bob fetches attacker's key from server, thinks it's Alice's
3. Bob encrypts message to attacker instead of Alice
4. Server relays attacker-encrypted message to Alice (who cannot decrypt)
5. Or server relays to Alice encrypted with attacker's key, which attacker can decrypt

**Current mitigation:** TOFU pins first-seen key. ECDSA-signed rotation chain.
**Missing mitigation:** Certificate pinning, out-of-band verification (QR/safety numbers), key transparency logs.

### Scenario C: Database Leak Metadata Exploitation

**Trigger:** Attacker gains read access to PostgreSQL (#3).

**Impact:**
1. All ciphertext available (cannot decrypt without keys, but...)
2. Full communication graph visible (sender, recipient, timestamps, message count)
3. Channel membership fully visible
4. Hub structure fully visible
5. If weak passwords exist, vaults can be brute-forced offline (#19)
6. Public keys available for targeted attacks

**Current mitigation:** Content is encrypted. Vault has PBKDF2 600K protection.
**Missing mitigation:** Database encryption at rest, metadata minimization, strong password enforcement, data retention policies.
